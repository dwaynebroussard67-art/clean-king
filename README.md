# Goodwork — interactive concept

A Phase 0 demo inspired by the Build Dossier for Andy Merchant. Goodwork is a placeholder name, not an assertion of franchise affiliation. All applicants, crew, shifts, metrics, sites and activity are invented. No customer or franchisor marks are used.

## Run locally

Requires Node.js 22 or newer (the installed Supabase SDK requires Node 22).

```sh
npm install
npm run dev
```

Open http://localhost:3000. Run `npm test` for unit/local database tests, `npm run build` for a production build, `npm run test:production` after a build for fail-closed configuration checks, and `npm run test:e2e` for mocked browser tests (first run `npx playwright install chromium`). GitHub Actions runs these plus a dependency audit. See `PRODUCTION_READINESS_PROGRESS.md` for current results and remaining blockers.

## What the demo does

- Review sample applicants, simulate decisions and toggle site clearance. These changes live only in browser memory and reset on reload.
- Simulate a school or hospital call-out. The sequence skips workers who are unavailable, lack Rookie Run or the applicable clearance, exceed an hour cap, or lack the health track for hospital work. The first eligible sample worker is assumed to accept; nobody is contacted or assigned.
- Preview a three-lesson sequence and simulate completion. There are no actual training videos, watch-time checks, certificates, or persisted records.
- Explore a scripted assistant, service templates and an owner page shell, in English or Spanish.

## Important limits before real use

The **demo at `/` is not a secure or production-ready system**. Its owner workspace is not authenticated and its actions do not send messages or save data. Separate, disabled-by-default intake and email-notification foundations are described below, but have not been deployed or verified with live providers. Do not enter real personal, school, patient, or customer data. The simulated Bench is not a scheduling engine: it does not implement offer timeouts, overlap detection, rotation, quiet hours, premium approvals, or concurrency control.

Before launch, confirm branding/franchise permissions, actual services and territory, site screening requirements, training sources and translations, and approved contact details. Implement passkeys and server-side authorization, database row-level security, consent and SMS registration, secure queues and atomic shift claims, privacy controls, and explicit approvals for external messages and sensitive actions. Review the dossier for the full requirements and open questions.

## Intake foundation (not yet approved for production)

The separate `/apply` and `/quote` pages and `/owner` inbox are the beginning of a real, persistent workflow. They are **off by default**. The demo at `/` remains fictional and is not connected to the inbox. Intake and development email-link login now fail closed whenever `NODE_ENV=production`, even if their flags are set. They can only be enabled for a controlled development/test environment; do not expose that environment publicly or enter real data. No project has been selected or modified, and nothing has been deployed.

- The two forms validate on the server, use an explicit Turnstile verification action and hostname, cap request body size, and insert using a server-only service key. The application has optional job-related experience questions and a review/edit step before submission; optional answers are stored with the applicant and visible in the protected owner inbox. The owner email does not include these additional answers. An idempotency key reconciles retries with the same request ID and validated content; it does not guarantee exactly-once submission across tabs or lost sessions. The application collects optional SMS consent, consent timestamp and wording version, plus the form language. It does not send any messages. Quote requests do not grant SMS consent.
- Owner accounts must exist in Supabase Auth **and** have a manually provisioned `owner_memberships` row. The inbox uses the signed-in user's session, not the service key; Postgres RLS and column grants restrict reads and updates. Status and clearance changes are recorded in the audit table without copying contact details. A development-only owner action can atomically mark an applicant hired and start an onboarding preparation record; no employee account, welcome message, verification, real training or schedule is created. The inbox uses independent newest-first keyset pagination for applications and quotes (25 per page), including a timestamp/ID tie-breaker. It still requires testing against an approved live Supabase project.
- Owner email-link login is a **development-only interim mechanism**, disabled by default and forcibly unavailable in production builds even if enabled in the environment. It is not the dossier's passkeys, approved-device enrollment, step-up authentication, or 90–180 day policy. Do not use it for real personal or sensitive data. Clearing a site flag is a manual owner action, not verification of a background check.

### Development setup on a dedicated test project only

1. Choose a dedicated Supabase project and apply all migrations in `supabase/migrations/` in timestamp order through the normal migration workflow. Do not apply it to another application's database. 2. Copy `.env.example` to `.env.local` and configure the project URL, publishable key, and server-only service role key. 4. Exercise the complete flow with synthetic data and validate the RLS policies against the actual Supabase deployment. `npm test` includes an embedded Postgres RLS test (PGlite omits the pgcrypto extension statement because it already provides `gen_random_uuid`); it does not replace deployment integration tests.

## Application emails to the owner (disabled by default)

A submitted application creates a notification record in the same database transaction. The application response does not depend on email delivery. After the response, the server attempts an immediate send; a separate scheduler is **required** for recovery and retry. An email contains first name, phone, area, availability, transportation, languages and referral, so Andy can read it and call from his phone without signing into the website. The email links to the protected inbox for decisions; there are no unprotected hire/pass links. Provider acceptance is not proof that an email reached a phone or inbox. Phone notification settings depend on the owner's email app.

Before using this with real applicants:

1. Obtain an approved, dedicated Supabase project and apply all migrations in timestamp order. The notification migration queues only applications submitted **after** it is applied; it does not backfill older records. Keep intake disabled until all migrations and the whole flow are verified.
2. Set up Resend, verify a sender domain, and configure its server-only key. Enter Andy's approved address in `APPLICATION_NOTIFICATION_TO` and a single verified sender address in `APPLICATION_NOTIFICATION_FROM` through the deployment environment, not source control. Set the canonical HTTPS `APP_ORIGIN`. Keep `APPLICATION_EMAIL_NOTIFICATIONS_ENABLED=false` until these and the privacy review are complete.
3. Configure a trusted scheduler to call `GET /api/jobs/application-notifications` with `Authorization: Bearer <CRON_SECRET>`. Set `CRON_SECRET` as a long random server-side secret (at least 32 characters). Vercel Cron can supply this header automatically when configured; schedule frequency and availability depend on the deployment plan. **No cron schedule is provisioned by this repository**. Use a frequent schedule, alert on non-200 responses, and monitor failed queue records. A job handles at most five messages per invocation. It also returns HTTP 503 when the queue has failed jobs, pending jobs more than 15 minutes past their available time, or processing leases older than two minutes; the response includes aggregate counts only. Configure independent monitoring of this endpoint and of the scheduler itself—no alert is automatically sent. If the scheduler is absent or broken, failed or interrupted sends will not be retried automatically.
4. Enable notifications only after a synthetic end-to-end test and privacy review, including that the recipient controls the mailbox and can receive personal information. Review data retention and email handling. SMS consent is unrelated to the owner's email notification; this code does not send applicant texts.

The queue uses database leases to prevent concurrent claims and exponential retry delays, with a maximum of eight attempts. Failed jobs require operator attention; no independent failure alert is implemented yet. For development, an authorized database operator can inspect `public.application_notifications` (no provider secrets or applicant details are stored there) and after correcting a problem reset a failed row to `pending`, set `attempts=0` and `available_at=now()`. Changes should be logged and performed only under an approved operational procedure. `sent` means the provider accepted the request, not that it was delivered. A stable provider idempotency key reduces duplicates for retries; Resend's idempotency window is finite, so a long outage or an uncertain response can still produce duplicate email. Do not change the recipient, sender, or origin while retrying an uncertain send without investigating it first.

## Owner assistant foundation (disabled by default)

The demo assistant on `/` remains scripted. A separate experimental `/owner/assistant` page and `/api/owner/assistant` endpoint can call OpenAI when explicitly enabled. It uses the existing **development-only** owner login plus server-verified owner membership on every request. The provider receives only the typed question and four aggregate counts: new applications, new quote requests, queued application emails, and failed application emails. It does not receive applicant records or site data through the snapshot. There are no tools, database writes, messages, scheduling, or actions accessible to the model. Because it relies on development-only login, the assistant is unavailable in production builds. It can still give an incorrect answer; never assume a statement means an action occurred.

The database migration `20261117020000_assistant_usage.sql` records only run metadata (owner, timestamps, result), not prompts or responses, and serializes admission to a workspace-wide limit of three attempts per minute and 100 attempts per UTC month. Failed calls count too. Input is capped at 2,500 characters, output at 400 provider tokens, and each question is independent. These request limits are **not a monetary spend cap**; pricing can change, so configure a provider-side billing limit and monitoring. Prompts are sent to the provider and subject to its data policy, so do not enter names, phone numbers, student/patient information, credentials or other sensitive data. No conversation memory, prompt logging, or key storage UI is implemented.

For synthetic testing only, apply all migrations in order to a dedicated test project, set the server-only `OPENAI_API_KEY`, and explicitly set `OWNER_ASSISTANT_ENABLED=true` alongside development owner login. Both default off. No live AI call has been tested in this environment. Before real use: replace email-link access with passkeys and approved-device controls; implement and verify a real spend cap, independent usage alerts, privacy review, secure secret management, adversarial testing, and provider-specific data retention settings. Future tools must be separately authorized in server code, logged, and subject to approval where appropriate; prompts alone are not a security boundary.

## Site guide and directions preview

The demo's **My site guide** screen is an invented example, not a crew portal. It has a tappable sample layout in English and Spanish and demonstrates where assigned-site details, instructions, supervisor contact and directions could appear. The demo directions button deliberately does not open a real address. No real floor plans, addresses, shift assignments, worker identity checks, or private file access are implemented; the preview is publicly accessible and must never be used for real site information.

### Research and recommended production design

- Google Maps URLs can open navigation on mobile or in a browser without an API key. The fixed-origin `directionsUrl()` helper encodes an approved address; it is not connected to real data yet. Opening a maps app shares the destination with that provider. [Google Maps URLs](https://developers.google.com/maps/documentation/urls/get-started)
- Schools and care facilities may treat floor plans and security information as sensitive. Get the customer's written permission, confirm what can be shared, and use the minimum information needed for the job. Do not put access codes, passwords, student or patient information, or observations about people in site notes. Do not treat a cleaning guide as an emergency map; follow the facility's current official emergency plan. [CISA physical security guidance](https://www.cisa.gov/sites/default/files/2022-11/Planning%20and%20Response%20to%20an%20Active%20Shooter_2021.pdf)
- Store site documents in a private bucket, not public assets. Supabase private buckets support access control, but signed links can be forwarded and individual signed URLs cannot be revoked; caches can also persist after access is removed. Prefer an authenticated, no-store server-mediated document response that checks current authorization on every request, and verify storage/cache behavior before launch. No approach can recall a screenshot or a file already saved on a device. [Storage access](https://supabase.com/docs/guides/storage/buckets/fundamentals), [signed URL limitations](https://supabase.com/docs/guides/storage/serving/downloads), [cache considerations](https://supabase.com/kb/troubleshooting/storage-private-bucket-files-still-accessible-after-remove-access-or-logout)
- A worker should see only their own current or approved upcoming assignments, not the full site roster. An unaccepted offer or backup designation alone should not grant access. The server must validate worker identity, active status, site eligibility, assignment and the owner-approved access window on every site and document request. A forwarded text link by itself is not proof of identity; use a short-lived sign-in flow with appropriate verification and revocation. Actual shift windows and verification method need owner and customer approval.
- Build mobile-first, with labeled, keyboard-accessible areas, readable non-map instructions, language support, document version/date and a way to contact the assigned supervisor. Confirm how floor plans will be supplied, who can approve or replace them, any client restrictions, and how updates are communicated. Build authorization and integration tests before any real site data is loaded.

## Experimental employee referral foundation (disabled)

`REFERRALS_ENABLED` defaults to false and additionally requires configured test intake and development email-link login. `/crew/referrals` is a **test-only** employee page; it is not a production account or onboarding system. With an active manually enrolled test employee, it creates a random single-use, seven-day invitation; the server stores only a SHA-256 hash. The raw code is displayed once; the link uses a URL fragment so the code is not sent in the initial page request. Share it only with the intended person: possession is enough to use it. A user can copy the link or use the device's share sheet. There is a ten-per-employee, rolling-day creation limit.

A validated and bot-verified application with a code is inserted atomically with immutable attribution and the existing notification outbox. The invitation is consumed only when the application commits; expired, used, or inactive-employee invitations fail. A retry with the same request ID and content is recognized; the form now keeps only its opaque request ID in session storage across reloads, never applicant data. Storage may be unavailable or a session may end, so this does not guarantee exactly-once submissions; employees see only counts, not applicant names, details or private decisions. The owner test inbox shows an internal employee ID and distinguishes verified attribution from self-reported referral text. Links do not access identity, contacts, social profiles or other data; the applicant supplies their own information (ordinary browser autofill may be used). The system does not yet record a separate application start, notify the referring worker, display hired/pending counts, handle corrections or rewards, or provide an employee directory. There is no real employee enrollment flow or approved authentication.

For isolated synthetic testing only, apply **all** migrations to an authorized dedicated test project, run the development server in a restricted environment, configure the existing intake and test login, and manually insert an already existing test Auth user into `public.employee_memberships` with a trusted administrator session. Set `REFERRALS_ENABLED=true` only in that controlled environment. A test employee can sign in using the existing development login, then navigate to `/crew/referrals` (the login callback currently lands on `/owner`). Do not use real applicant data. Check two separate devices or browser contexts and test concurrent/expired/revoked invites, recovery after network loss, live RLS and outbox delivery; these have not been verified against live services. Keep off for production until passkeys or appropriately secure employee authentication, dedicated onboarding, WAF/rate limits, audit/recovery, privacy/retention, accessibility, translation, security review and provider tests are complete. Invitation creation cannot be undone or recovered in this prototype; an unused invitation expires after seven days. A worker can create a new one instead.

### Application questions and review (synthetic testing only)

The application can collect optional professional experience, commercial/residential and equipment experience, and willingness to train. Unanswered questions are saved as null, not as “no.” The applicant can review the entered data, return to edit it, and then submit; a successful review alone does not send or save anything. The questions are not automated screening and never make a hiring decision. Legal and fairness review, approved translations and real provider testing are required before real use. The experience migration `20261117040000_application_experience.sql` must be applied after the referral migration even when referrals are disabled; deploying the updated intake code before all migrations will cause submissions to fail. Requests left open across a deployment can conflict on retry because the validated content shape has changed; coordinate rollout and test uncertain-response recovery.

### Owner-approved onboarding preparation (synthetic testing only)

The owner test inbox's **Hire & start onboarding** action creates one `employee_onboarding` preparation record and three owner-note tasks in the same transaction that marks the applicant hired. The record references the existing applicant instead of copying identity information. The tasks are reminders to review employment documents, plan training and plan the first shift; “Owner noted” means only that an authorized owner recorded a note, not that documents, legal eligibility, training or work have been verified. Actions and note changes are audited without copying personal details. A passed applicant must be reopened before onboarding; an existing hired applicant without a record can be explicitly brought into this preparation workflow. Once hired, the ordinary status buttons cannot undo that decision; an authorized separation/correction workflow has not been implemented.

This is **not employee account creation or activation**, and it does not send a welcome message, assign training, schedule a shift or authorize site access. Owner and worker authentication, employee lifecycle, official records, concurrency testing on live Postgres, data-retention/deletion policy and legal review remain required. Applicant/onboarding foreign keys deliberately prevent automatic deletion; design and test an approved deletion/retention process before using real data. The migration must be installed together with the matching server actions; do not deploy either piece alone. Local PGlite and mock-integrated tests do not replace a live two-device test.
